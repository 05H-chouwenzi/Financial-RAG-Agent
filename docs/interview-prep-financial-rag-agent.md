# 第一部分：简历项目深挖（最容易被问，先背熟）

## Q1. 一句话介绍你的项目

**话术（30 秒版）：**
> 我搭了一个面向 A 股上市公司年报的垂直金融 RAG 系统。从巨潮资讯网下载年报 PDF，做版面感知解析和结构感知切块，然后用"BM25 词法 + bge 向量 + RRF 融合 + bge-reranker 重排"的混合检索，最后接 DeepSeek 生成答案，并且带引用溯源、数字校验和拒答三个安全机制。整个系统用 golden set 做量化评估闭环，69 条真实问题上检索 Hit@5 做到 100%、MRR 81.5%，端到端生成也有 RAGAS 和数字校验通过率指标。

**追问：为什么不叫"通用 RAG"？**
> 金融场景有三个特殊性：一是数据是 200 页大表格年报，普通切块会把表格切烂；二是答案里的**数字不能错**，差一个零就是事故；三是问题类型多（事实、表格、对比、计算、拒答），所以要专门做意图识别和数字校验。

## Q2. RAG 是什么？你的完整流程讲一遍（必考，要能徒手画）

**话术：**
> RAG 就是检索增强生成，先从知识库检索相关片段，再让 LLM 基于片段生成，解决 LLM 幻觉、知识过时和私有数据问题。我的流程分离线和在线两段：
> - **离线**：巨潮下载 PDF → 解析成 LayoutBlock（标题/段落/表格/页码/阅读顺序）→ 结构感知切块（表格不切破）→ 构建稠密向量索引（FAISS）+ 词法索引（jieba BM25）。
> - **在线**：用户问题 → 意图识别（fact/table/compare/calc/reject）→ 混合检索（BM25 + 向量，RRF 融合 Top30）→ bge-reranker 重排取 Top5 → 生成（引用溯源 + 数字校验 + 拒答）。

## Q3. 你遇到的最大困难是什么？怎么解决的（重点题，讲"检索不到指标表"这个故事）

**话术（建议背这个版本）：**
> 最大的坑是"财务指标表检索不到"。我一开始用纯向量检索，发现问"茅台 2023 年营收"这种问题，模型经常命中年报里审计政策的"收入确认"段落，而不是"主要会计数据"那几张关键表格，因为财务表格文本稀疏、又长又大，向量相似度不高。我当时做了四件事：
> 1. **候选池放大**：融合候选从 Top10 放大到 Top30，让指标表先进候选；
> 2. **表格/指标锚定加权**：解析时把"主要会计数据"这类核心表格块打上标记，pre-rerank 加权 ×2，重排阶段再加 0.10 的锚定分；
> 3. **元数据增强**：chunk 带公司名、年份、报告类型、章节路径，词法重排时用 search_text 算重叠率，避免表格块原文没公司名年份导致词法分被低估；
> 4. **时间/报告期过滤**：问 2023 就优先 2023 的报告。
> 做完后"茅台 2023 营收"这类问题从命中审计段落修到指标表进 top-1。整体检索 Hit@5 从 47.4% 提到 94.7%，再优化到 100%，MRR 从 23.4% 提到 81.5%。

**为什么讲这个故事好**：有"现象→分析→方案→数据验证"完整闭环，是面试官最爱听的结构化回答。

## Q4. 数据从哪来的？合规吗？

**话术：**
> 从巨潮资讯网公开接口下载年报/半年报，它本身就是 A 股法定披露平台，公开免费，版权合规——这是我不做券商研报的原因，研报版权难拿。下载器做了限速（0.8s/请求）、重试、断点续传，用 manifest.csv 记录每个 PDF 的状态。目前语料是贵州茅台 + 平安银行 2023/2022 年报等 8 份真实报告。

## Q5. PDF 解析难点怎么处理？（表格/多栏/扫描件）

**话术：**
> 年报 PDF 三大难点：**大表格**（一页几十行、跨页）、**多栏排版**、**扫描件**。我的解析器分三层：pdfplumber/PyMuPDF 抽文本和表格做 baseline；版面层输出统一的 LayoutBlock 结构（块类型、页码、bbox、阅读顺序、章节路径），保证表格整体成一个块不拆散；扫描件留了 OCR 集成点（PaddleOCR/MinerU），目前真实数据是文字版 PDF，还没到必须上 OCR 的程度。解析质量有自评：表格行列还原率、文字保真率、解析失败率。

## Q6. 为什么混合检索而不是纯向量？

**话术：**
> 纯向量擅长语义匹配但**不擅长精确匹配**——金融里"2023 年""56.88 亿元""000001"这种词，语义向量容易忽略；BM25 擅长精确词匹配但不理解语义，比如"净利润"和"归母净利"这种说法就召回不到。所以两路取长补短，用 RRF 融合。我做了 A/B：dense-only 的 Hit@5 只有 81.2%，混合后 100%，MRR 从 61.3% 提到 81.5%，说明融合是真有效的。

## Q7. 重排的原理？为什么只用重排结果生成？

**话术：**
> 向量检索是双塔，query 和 doc 分开编码算相似度，快但粗；重排用 bge-reranker 这种**交叉编码器**，把 query 和 doc 拼在一起过一个 Transformer 精排，准但慢，所以只对融合后的 Top30 重排取 Top5，兼顾质量和速度。重排阶段我还会给指标表核心块加分，解决表格被挤掉的问题。

## Q8. 你的评估体系怎么搭的？（重点，详见第四部分）

**话术：**
> 我搭了三层：一是 **golden set**，从真实年报里人工出题标注，每条有 question、标准答案、证据片段、来源文档页码、类型标签（fact/table/compare/calc/multi_doc/reject），目前 69 条真实 + 8 条演示；二是**检索指标**，Hit@k、Recall@k、MRR、NDCG，我全部用纯 Python 自己实现，不依赖库，所以每条指标的公式我都能讲清楚；三是**生成指标**，数字校验通过率、拒答准确率，外加 RAGAS 的 faithfulness / answer_relevancy / context_precision / context_recall。每次改动只动一个变量，跑全量回归，出报告存到 experiments 目录，保证可复现。

## Q9. 拒答怎么实现？

**话术：**
> 三层拒答：第一层**意图识别**，问题里带"预测/股价/涨停/买入/未披露/明年业绩"这些关键词直接拒，不浪费检索；第二层**阈值拒答**，检索最高分低于 0.10 就拒，说明知识库里没有相关内容；第三层**生成后校验**，回答里的数字在证据里找不到就修正或拒。真实测试里拒答准确率 100%。

## Q10. 数字校验怎么实现？

**话术：**
> 金融最怕数字幻觉。我的做法是：先把回答里所有数字抽出来（长度 ≥3 位的），再和检索证据文本里的数字比对。难点在**单位换算**——回答可能写"1476.94 亿元"，年报原文写"14,769,360.50 万元"，直接字符串比对会误报。所以我做了单位归一：把带单位的金额都换算成"元"再比，容忍 1% 相对误差；裸数字则按常见单位（千/万/百万/亿）逐个试算。年份数字单独放宽，因为年份不是数据。做完后数字校验通过率从 73.7% 提到 78.9%，剩余误报主要来自回答里的解释性数字（比如"增长 19.16%"里的 19.16 是算出来的）。

## Q11. 金融 Agent 的意图识别怎么做的？

**话术：**
> 目前是**关键词规则**实现的轻量意图识别：先查拒答关键词（预测/股价/推荐），再查计算类关键词（ROE/毛利率/资产负债率）走工具计算，再查表格类（股东/持股/占比）和对比类（对比/相比/变化），默认 fact。计算类问题会从检索证据里用正则提取字段，套公式算指标（ROE=净利润/净资产、毛利率=(营收-成本)/营收），算不出来就退回普通 RAG。下一步计划升级成 LLM 分类器。

## Q12. 性能、成本考虑过吗？

**话术：**
> 提过三个点：一是重排只对 Top30 精排，控制延迟；二是本地部署 bge 向量和 bge-reranker（FlagEmbedding），不依赖付费 embedding API，DeepSeek 只承担生成；三是词法重排兜底（RERANK_BACKEND=lexical）用于批量评估加速，因为交叉编码器在几百条评估上很慢。延迟/成本的 p50/p95 还没有正式压测，这块我可以补。

## Q13. 如果让你再加一个功能，你加什么？

**推荐答案（体现思考）：**
> 我会加**查询改写/追问澄清**——很多用户问题是不完整的，比如"毛利率是多少"没说哪一年哪家公司，用 LLM 结合对话上下文补全查询，或者反问用户澄清；其次是**增量更新**，新财报出来只解析新增文档、局部更新索引，不用全量重建；第三是**表格更精细的问答**，把表格块还原成结构化 JSON，支持"第几列第几行"这类精确取数。

## Q14. 你和别人简历上的 RAG 项目，差异在哪？

**话术：**
> 多数 demo 项目是"装个 LangChain 调 API 就能跑"，我的差异化有三点：一是**数据是真的**，巨潮真实年报，不是玩具文档；二是**评估闭环是真的**，69 条人工标注 golden set + 自实现指标 + A/B 实验，每个优化都有数字证明；三是**金融安全机制**，引用溯源、数字校验、拒答不是 PPT 上的词，是真实跑通并测过通过率的代码。

| 什么是 Embedding？ | 把文本映射成固定维度向量，语义相近的向量距离近；双塔模型（query/doc 各一个 encoder）训练 |
| 向量检索怎么算相似度？ | 余弦相似度 cos(q,d)=q·d/(‖q‖‖d‖)，或内积、L2 距离；FAISS 建索引做 ANN 近似最近邻 |

| BM25 公式背得出吗？ | score = Σ IDF(qi) · [f(qi,D)·(k1+1)] / [f(qi,D) + k1·(1-b+b·|D|/avgdl)]，k1≈1.2~2，b≈0.75 |

| 为什么切块？多大合适？ | LLM 上下文有限、检索粒度要细；我默认 600 字 + 80 重叠；关键是不能切破表格，超大表按行组切且保留表头 |

| 交叉编码器 vs 双塔？ | 双塔 query/doc 分开编码可预计算索引，快；交叉编码器拼一起编码，准但慢，适合重排 |
| RAG 有哪些幻觉缓解手段？ | 引用溯源、数字/事实校验、拒答、检索质量提升、更严格的 prompt、答案生成后校验 |

# 第三部分：金融场景专精（体现垂直差异化）

1. **数字敏感**：金融回答错一个数字=事故，所以数字校验是本项目灵魂（Q10）。
2. **单位口径**：亿元/万元/百万元/千元混用，表头标注口径时单元格裸数字，需归一化匹配。
3. **时间口径**：年报/半年报/一季报时间不一致，必须按报告期过滤（"2023 年末" vs "2023 年半年度"）。
4. **公司/报告类型口径**："平安银行 2023 年报"和"平安银行 2023 半年报"数字可能不同，元数据里带 report_type 并区分。
5. **表格为王**：年报核心数据全在表格里，表格还原质量直接决定 RAG 上限。
6. **合规边界**：只答已披露事实，拒答预测/股价/投资建议/内幕（拒答关键词表）。
7. **术语**：ROE、毛利率、净利率、资产负债率、拨备覆盖率、净息差、成本收入比、资本充足率、每股收益、扣非净利润——面试至少能解释 5 个。
8. **计算类问题**：ROE=净利润/净资产；毛利率=(营收-成本)/营收；净利率=净利润/营收；资产负债率=负债/资产；同比增长=(本期-上期)/上期。
9. **多文档对比**：跨年度/跨公司对比要靠元数据锁定 doc_ids，防止拿错年份。
10. **引用溯源**：每条答案带 [n] 来源（公司名+年份+报告类型+页码），这是金融场景的硬要求。

# 第四部分：评估指标 —— "指标怎么来的"（重点，背话术）

> 这是你最需要的部分。核心逻辑一句话：**所有指标都来自 golden set + 公式，没有任何一个数是拍脑袋的。**
> 通用推导流程（每个指标都走这 5 步）：
> 1. **标注**：golden set 每条问题人工标出"证据片段"（evidence），evidence 对应到具体 chunk 的 index；
> 2. **跑检索**：对每条问题调用 retriever，得到排序后的 chunk 列表（index 序列）；
> 3. **判相关**：某 chunk 的 index 在 relevant set 里 = 相关；
> 4. **套公式**：对每条问题算出该指标的数值；
> 5. **聚合平均**：对所有问题求平均，得到报告里的总指标。
>
> 代码位置：`backend/src/eval/metrics.py`（检索指标）、`backend/src/eval/runner.py`（评估主流程）、`backend/src/eval/golden_set.py`（golden set 加载）、`backend/src/eval/ragas_eval.py`（RAGAS）、`backend/src/generation/checks.py`（数字校验/拒答）。

## 4.1 Hit Rate@k（命中率）—— 最重要、必背

**公式：** HitRate@k = (1/N) × Σ 1[ 前 k 个结果里至少有一个相关 chunk ]

**怎么来的（口述版）：** 对 golden set 里每条问题，我人工标了答案所在的证据 chunk；跑检索后看这个 chunk 在不在返回的前 k 个里，在就算这条命中（1），不在就 0；把所有问题的命中率平均。

**项目话术：**
> Hit@k 看的是"答案相关的证据块能不能被捞回来"。我 69 条真实问题上 Hit@5 = 100%，说明所有问题的证据块都能进前五；Hit@3 = 94.2%，说明前三个基本也能命中。这个指标是最先看的，因为它决定了 RAG 的天花板——检索捞不到，后面生成再强也没用。

**追问防御：** 面试官可能问"Hit@k 高但 Recall 低矛盾吗？"——答：不矛盾。Hit@k 是"有没有命中至少一个相关块"，只要 1 个相关块进前 k 就满分；Recall@k 是"捞回了多少比例的相关块"。我的相关块通常每问只有 1~2 个，所以 Recall@5 只有 5.1%，说明语料里大部分 chunk 都不相关，这很正常，也说明评估里的 relevant set 是精确标注的。

## 4.2 Recall@k（召回率）

**公式：** Recall@k = (1/N) × Σ ( 前 k 中命中的相关块数 / 该问题总相关块数 )

**怎么来的：** 对每条问题，数前 k 个结果里命中了几个相关块，除以这条问题总共有几个相关块，再平均。

**项目话术：** 我的标注比较严格，一个问题一般只标 1~2 个核心证据块，所以 Recall 天然偏低（5.1%）；它更反映"多证据问题能不能捞全"，比如对比类问题要同时捞到两年的表，我才更关注 Recall。

## 4.3 MRR（平均倒数排名）—— 第二个必背

**公式：** MRR = (1/N) × Σ 1 / rank(第一个相关结果的排名)

**怎么来的：** 每条问题找到第一个相关 chunk 的排名 r，取倒数 1/r；第一名=1.0，第二名=0.5，第三名=0.33……没命中=0；平均。

**项目话术：**
> MRR 看的是"第一个正确答案排多靠前"。69 条真实问题 MRR=81.5%，意味着平均下来第一个正确答案基本排在第二位以前。A/B 里 dense-only 只有 61.3%，混合+重排后 81.5%，说明重排把正确答案往前顶了。如果 MRR 高但 Hit 低，说明"捞到但排太后面"，重点就放在重排和融合。

**追问防御：** "MRR 满分是多少？怎么才能 100%"——答：每条问题第一个相关块都排第一就 100%。我逐条报告里有几条 MRR=0.2/0.25，比如"每 10 股派息"这种，证据块进前五了但排第三第四，所以是重排的优化点。

## 4.4 NDCG@k（归一化折损累积增益）—— 面试加分项

**公式：** DCG@k = Σ ( rel_i / log2(i+1) )；NDCG@k = DCG@k / IDCG@k（IDCG 是理想排序下的最大 DCG）

**怎么来的：** 把排序当成"打分序列"：第 i 位的相关块得 rel_i=1，不相关得 0，但**位置越靠后权重越小**（log2 折损）；DCG 除以理想排序的 DCG 归一化到 0~1。

**项目话术：** NDCG 比 Hit 更严格，它惩罚"相关块排后面"。我的 NDCG@5=57.6%，比 Hit@5=100% 低很多，就是因为很多问题证据块虽然进前五但不在第一位——这正好点出重排还有提升空间。A/B 里从 dense-only 的 30.9% 提到 57.6%，说明我的优化是真的把排序质量拉上来了。

## 4.5 Precision@k（补充，可能被问）

**公式：** Precision@k = (前 k 中相关块数) / k

**人话：** 返回的 k 个结果里有多少是相关的。我的场景相关块少，Precision 会很低，所以主指标用 Hit/MRR 而不是 Precision——这个取舍也可以主动讲给面试官听，显得懂行。

## 4.6 RAGAS 四件套（生成质量，LLM 打分的指标）

**共同点：** 这几个指标**不是公式算的，是让 LLM 当裁判打分**的。做法：把"问题、回答、检索到的上下文、标准答案"喂给 LLM，LLM 按规则给 0~1 分，然后平均。所以它们叫"LLM-as-a-judge"指标，比公式指标贵、慢，但能测生成质量。

| 指标 | 在测什么 | 怎么打分 | 项目数字 |
|---|---|---|---|
| Faithfulness（忠实度） | 回答有没有编造，是不是都来自上下文 | LLM 把回答拆成句子，逐句问"这句能不能被上下文支持"，支持的比例 | 逐条 0.25~1.0，说明有的回答有少量超出上下文的解释性内容 |
| Answer Relevancy（答案相关性） | 回答是不是答非所问 | 用向量算"问题↔回答"相似度（我复用本地 bge 向量） | ≈0.79~1.0，整体很高 |
| Context Precision（上下文精确度） | 检索回的上下文里相关的是不是排前面 | LLM 判断每段上下文是否相关，按位置折损 | 0.2~1.0，波动大，是检索排序问题的投影 |
| Context Recall（上下文召回） | 标准答案的要点被上下文覆盖了多少 | LLM 把标准答案拆句，逐句问"上下文里有没有" | 1.0（19 条全满分） |

**项目话术（重点背这个）：**
> RAGAS 是行业标准生成评估库，但它依赖 LLM 打分。这里有个工程坑：我的 LLM 是 DeepSeek，它不支持 embeddings 接口、只支持 n=1，所以 AnswerRelevancy 的向量部分我复用了本地 bge-small-zh-v1.5 做 embeddings，LLM 打分走 langchain 包装的 OpenAI 兼容客户端；同时把并发调低、超时调大，否则长链指标会超时。19 条真实样本上 ContextRecall=1.0、AnswerRelevancy≈0.9+，Faithfulness 均值偏低（0.5 左右），原因是回答里带了解释性/推导性数字，这说明下一步可以优化 prompt 让回答更贴证据。

## 4.7 数字校验通过率（金融特有）

**怎么来的：** 跑生成时，对每条回答抽数字 → 和证据文本比对（含单位换算）→ 全部命中算"通过"；通过数 / 总条数。

**项目话术：** 数字校验通过率从 73.7% 提到 78.9%（加了单位换算匹配后），剩下的误报是回答里的解释性数字（比如算出来的增长率），不是真错误。这个指标是金融场景最有说服力的，因为直接对应"数字幻觉"这个核心风险。

## 4.8 拒答准确率

**怎么来的：** golden set 里专门标了 reject 类问题；跑完后看"该拒的是不是拒了、拒的理由对不对"。

**项目话术：** 真实测试 3 个拒答样本全部正确拒答，准确率 100%。实现上是关键词意图识别 + 阈值双重保险。

## 4.9 端到端准确率 / 人工抽样

**怎么来的：** 对 golden set 全链路跑完，人工（或 LLM 辅助）判"答案对不对"，对的比例。RAGAS 是自动化版本，人工抽样是最终兜底。

**项目话术：** 我目前 RAGAS 是自动化的，人工抽样做了小批量；端到端准确率需要标完整答案比对，是下一步要补的。

## 4.10 工程类指标（可能被问：延迟 / 成本 / 解析质量）

| 指标 | 怎么测 | 话术 |
|---|---|---|
| 延迟 p50/p95 | 压测工具（locust/自写脚本）打 /api/chat，统计耗时分布 | "还没正式压测，检索是毫秒级，瓶颈在 LLM 生成；重排只精排 Top30 就是为了控延迟" |
| 成本/query | 按 token 计费估算 | "向量和重排本地部署不花钱，只有 LLM 生成花钱，DeepSeek 很便宜" |
| 表格还原率 | 解析后和原 PDF 表格比对，行/列/单元格还原比例 | "解析层自评指标，目前真实报告是文字版 PDF，表格还原率较高；扫描件要上 OCR" |

# 第六部分：场景设计题（开放题，中小厂爱问）

## 场景 1：老板让你把 500 万份研报/公告都接进来，你怎么设计？

> 要点：数据分层（元数据先行）、增量更新（manifest 记录已处理，只处理新增）、解析流水线化（PDF→LayoutBlock→chunk 可断点重跑）、索引分片/按公司分库、任务队列（异步）、抽样质检（解析失败率监控）、成本控制（OCR 只处理扫描件）。

## 场景 2：用户问"茅台股价明天会涨吗"，怎么处理？

> 拒答。合规红线：不预测、不荐股。话术：明确告知只能基于已披露年报/公告回答事实问题，给出拒答模板。

## 场景 3：用户说"毛利率是多少"，但没说是哪家哪年，怎么办？

> 澄清/默认策略：对话上下文补全（如果之前聊过茅台就用上下文），否则反问"您问的是哪家公司、哪一年？"；这对应我 Q13 里的下一步计划。

## 场景 4：回答错了被用户投诉，你怎么排查？

> 分层排查：检索捞没捞到证据（看 Hit/MRR、看 top-k 日志）→ 重排有没有把证据顶掉 → LLM 有没有照着证据答（看 faithfulness）→ 数字校验有没有拦住（看校验日志）。我现在的系统每一步都有日志和引用块，能定位到具体环节。

## 场景 5：没有标注数据（冷启动），你怎么建 golden set？

> 三阶段：先用 LLM 生成草稿问题（让 LLM 读报告出题）→ 人工校验，确保 evidence 真实存在 → 类型分布对齐（fact/table/compare/calc/multi_doc/reject 配比）。我的 `scripts/build_golden_set.py` 就是"LLM 出题 + 人工校验"的流程。

## 场景 6：新财报发布，怎么更新知识库？

> 增量：manifest.csv 记录已下载版本 → 新 PDF 走解析切块建索引 → 只更新增量索引，不重建全库；同一公司旧报告保留用于对比类问题，但要靠报告期元数据区分。

## 场景 7：200 页年报，检索经常错过中间章节的表格？

> 结构感知切块（按章节）+ 章节路径元数据 + 表格块加权 + 候选池放大 + 层级检索（先章节再段落）。

## 场景 8：怎么评估"这个 RAG 系统好不好"？

> 分三层讲：检索层（Hit/MRR/NDCG）+ 生成层（RAGAS/数字校验/拒答）+ 用户层（人工抽样/线上反馈）。核心是有 golden set 闭环，改一次跑一次回归。
